# RetailMind AI

A retail decision-intelligence platform: it explains *why* a number moved,
forecasts what's next, and recommends what to do about it — grounded in your
own data, never invented by a model.

## What is RetailMind?

RetailMind is a working retail analytics and decision-intelligence platform
for mid-market retailers. A retailer connects their sales (and, optionally,
inventory, purchasing, fulfilment, and weather) data; RetailMind builds an
analytics warehouse from it, explains what changed and why, forecasts
demand, and proposes ranked, evidence-backed actions — accept or dismiss
each one, and the platform tracks whether it actually helped.

It's built as one platform serving many companies, not a single-tenant demo
wearing a "multi-tenant" label: each company's analytics warehouse is a
physically separate file, proven by running two independently-built tenants
through the same live API and confirming neither can see the other's data.

## Problem

A retail team can see revenue drop 8% but not *why* — was it one region,
one store, a pricing change, or a stockout? Spreadsheets show the number;
they don't decompose it, forecast around it, or tell you what to do next.
Most "AI retail analytics" tools either bolt an LLM onto raw numbers (and
risk it inventing a plausible-sounding but wrong explanation) or require a
data team to build a custom warehouse before anyone sees a dashboard.

## Solution

RetailMind separates **what the data proves** from **what a model
narrates**. Every number on screen is computed by a deterministic
analytical engine over a governed semantic layer — never generated by an
LLM. An optional language model (defaults to a deterministic mock; a real
Anthropic key is opt-in) only narrates evidence that already exists — it
explains, it doesn't invent. Onboarding is built around this same
discipline: a company's own column names are detected and mapped to a
canonical schema with a real, inspectable confidence score, not guessed
silently.

## Core Capabilities

- **Retail analytics** — 23 governed analytics domains (revenue, inventory,
  customers, suppliers, and more) over a semantic layer that compiles
  requests to parameterized SQL; application code never writes SQL by hand.
- **Anomaly / movement detection** — six alert detectors with suppression,
  so a real signal isn't buried under noise.
- **Root-cause analysis** — nine dimensional investigators with statistical
  decomposition and explicit confidence tiers (arithmetic → mechanical →
  statistical → associative); states plainly when a cause can't be
  established rather than guessing.
- **Forecasting** — hand-written ridge regression (no black-box library),
  scored against a seasonal-naive baseline (MASE) so a forecast that adds
  no information is flagged, not hidden.
- **Recommendations** — seven generators produce ranked actions with
  expected impact, risk (including reversibility and downside), and
  assumptions explicitly marked evidenced vs. unevidenced.
- **Decision intelligence** — a real decision ledger: accept/dismiss with
  reason codes, and a calibration engine that checks whether past estimates
  matched reality.
- **Natural-language analytics** — a deterministic query planner, not a
  text-to-SQL model. Questions outside its governed vocabulary are refused
  explicitly, never approximated.
- **Multi-tenant onboarding** — company profile, dataset detection, and
  column-name mapping work today for arbitrary CSV schemas; self-serve
  signup and browser-based upload are the next step (see [Current
  Limitations](#current-limitations)).

## How It Works

```
Customer data (CSV: sales, optionally inventory/purchasing/fulfilment/weather)
        │
        ▼
Dataset detection & column mapping   (real confidence scoring, human-reviewable)
        │
        ▼
Validation                            (missing fields, bad dates, out-of-range values — reported, not silently dropped)
        │
        ▼
Ingestion → dbt transforms            (67 models: staging → marts → semantic views)
        │
        ▼
One warehouse file, this tenant only  (physical isolation — see Architecture)
        │
        ▼
Analytics · Forecasting · RCA · Recommendations   (all read the same governed semantic layer)
        │
        ▼
Executive dashboard, investigation, decision center, forecasts — over HTTP, in the console
```

## What Users Provide

| Tier | Datasets | Unlocks |
|---|---|---|
| **Required** | Sales | Revenue trends, product/store performance, sales forecasting |
| **Recommended** | Inventory, Purchase Orders | Stockout detection, replenishment recommendations, supplier/lead-time analysis |
| **Optional** | Fulfilment, Weather | Delivery/operations signal, weather-linked demand effects (via RCA) |

Nothing is required beyond Sales — the platform is honest about which
capabilities are unavailable when an optional dataset isn't connected,
rather than showing an empty chart pretending it has data.

## What Users Receive

- An **executive dashboard** scoped to their own tenant — revenue, growth,
  ranked alerts, and the single highest-value action, all real, none
  fabricated to fill space.
- **Investigations** that carry context from a dashboard click through to a
  full root-cause breakdown, with what was checked and what wasn't.
- A **decision center** with ranked recommendations, each with expected
  impact, risk, and accept/dismiss tracking.
- **Forecasts** with prediction intervals and an honest accuracy scoreboard
  (a model that doesn't beat a naive baseline says so).
- **Outcome tracking** — a calibration engine that measures whether past
  recommendations' projected impact actually happened.

## Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                         STREAMLIT UI                             │
│  Command Center · Investigation · Decisions · Analytics · ...   │
│         (renders API responses only — holds no business logic)  │
└────────────────────────────┬──────────────────────────────────┘
                              │ HTTP/REST (JWT)
┌────────────────────────────▼──────────────────────────────────┐
│                       FASTAPI BACKEND                            │
│   Analytics · RCA · Forecasting · Recommendations · NLQ          │
│   · Analyst (optional LLM narration over verified evidence)      │
│                              │                                    │
│                    ┌─────────▼─────────┐                         │
│                    │  Semantic Layer   │──── the ONLY path to    │
│                    │  (governed        │     the warehouse,      │
│                    │   registry)       │     enforced by         │
│                    └─────────┬─────────┘     import-linter       │
│                              │                                    │
│              per authenticated tenant, resolved from the JWT     │
│                              │                                    │
│               ┌──────────────┴──────────────┐                    │
│               ▼                              ▼                    │
│      Tenant A's DuckDB file         Tenant B's DuckDB file        │
│      (physically separate —         (physically separate —       │
│       no shared table to leak       no shared table to leak      │
│       across, no WHERE clause       across, no WHERE clause      │
│       to forget)                    to forget)                   │
└─────────────────────────────────────────────────────────────────┘
                              ▲
┌─────────────────────────────────────────────────────────────────┐
│                      DATA PLATFORM                                │
│  CSV → detection/mapping → validation → ingestion → dbt (67 models│
│  across staging/marts/semantic) → one warehouse file per tenant   │
│  Orchestrated by Dagster (schedules/sensors); CLI available too   │
└─────────────────────────────────────────────────────────────────┘
```

Postgres (not pictured) holds everything OLTP — users, roles, decisions,
notifications — scoped by `tenant_id` at the model level, independent of
the warehouse-isolation boundary above.

### Technology Stack

| Layer | Stack |
|---|---|
| Backend | FastAPI, SQLAlchemy 2.0 (async), PostgreSQL 16, JWT (RS256), Celery/Redis |
| Data platform | Python (custom ETL), dbt 1.8+ (67 models), Dagster, DuckDB (one file per tenant) |
| ML | NumPy (hand-written ridge regression) — no scikit-learn, no XGBoost |
| UI | Streamlit, Plotly — 13 workspaces |
| Infra | Docker Compose, Nginx (TLS termination), Prometheus |

Full detail: [Architecture](docs/architecture.md),
[Multi-Tenancy Architecture](docs/multi-tenancy-architecture.md).

## Quick Start

```bash
make demo
```

This builds current-code Docker images, generates a synthetic demo
retailer's data (skipped if `.local/demo/retailmind.duckdb` already exists,
so the second run is fast), runs the dbt transforms, and starts every
container (Postgres, two Redis instances, MinIO, API, worker, beat, UI) —
migrations and seeding run as compose services before the app comes up.

## Security

- **Authentication:** JWT (RS256). Multi-worker deployments require a
  configured signing key — an unconfigured key in dev mints an ephemeral
  one per process (documented, known trade-off; see
  [Known Issues](docs/known-issues.md)).
- **Authorization:** RBAC with 6 roles, enforced at the API layer on every
  request — the UI hides what a role can't use, but the enforcement is
  server-side and would refuse the same request if the UI didn't hide it.
- **Tenant isolation:** enforced at two independent layers — `tenant_id`
  scoping on every OLTP table (Postgres), and a physically separate DuckDB
  warehouse file per tenant (no shared file, no filter to forget). Proven
  with real cross-tenant attack tests, not just architecture description —
  see [Multi-Tenancy Architecture](docs/multi-tenancy-architecture.md).
- **Secrets:** never in `.env` committed to the repo (gitignored); the
  `*_FILE` convention mounts secrets from files in production rather than
  environment variables. No secret of any kind exists anywhere in this
  repository or its git history — verified directly, not assumed (see
  [Public Release Audit](docs/prompt-14-public-release-audit.md)).
- **Self-conducted security review:** MEDIUM overall risk, 0 critical
  findings, 2 high, 4 medium, 3 low — see
  [Security Audit](docs/security-audit.md) for the actual findings (this is
  a self-review, not a third-party audit).
- **Reporting a vulnerability:** see [SECURITY.md](SECURITY.md).

## Current Limitations

Stated plainly, not smoothed over:

- **No self-serve company signup or browser-based file upload.** Creating a
  new tenant and provisioning its warehouse is currently an operator
  (database/CLI) step — the underlying detection/mapping/validation engine
  is real and works (`retailmind-etl onboard <file>`), but nothing wires it
  to a signup form yet. See [Company Onboarding](docs/company-onboarding.md).
- **LLM narration defaults to a deterministic mock.** A real Anthropic key
  is opt-in (`RM_LLM_ANTHROPIC_API_KEY`); business numbers never come from
  the LLM either way — it narrates evidence that already exists.
- **No Airflow, no Kubernetes, no Terraform.** Orchestration is Dagster;
  deployment is Docker Compose. Not gaps against a plan — deliberate scope.
- **Backups are opt-in, not automatic.** Scripts exist and are verified,
  but only run if `compose.prod.yml` is started with `--profile backup`;
  no offsite/managed backup target is configured.
- **Prometheus alert rules evaluate; nothing receives their
  notifications** — no Alertmanager is deployed.
- **One known, pre-existing test failure** (a Streamlit test-harness
  fragility, not a product defect) — see
  [Known Issues](docs/known-issues.md) for the complete, current list.
